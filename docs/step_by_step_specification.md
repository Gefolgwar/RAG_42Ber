## 1. Аналіз та вибір еталонної архітектури

Під час аналізу студентських рішень у каталозі `examples/` встановлено такі вимоги до проєкту:
- **Відмова від переускладнення (over-engineering):** Рішення не повинно плодити фабрики абстракцій, важкі інтерфейсні надбудови або надмірну кількість дрібних файлів (негативний досвід `Rebillard` та `69Nesta`).
- **Відмова від прихованих сторонніх залежностей:** Система не повинна залежати від непрозорих механізмів підрахунку символів у `langchain` (`sousampere`) або запущеного в ОС зовнішнього демона `Ollama` (`69Nesta`), оскільки це гарантовано ламає автоматизовану перевірку Moulinette в ізольованому кластері 42.
- **Вибір надійного ядра:** Використання підходу прямого парсингу Python через `ast`, прозорого розбиття Markdown за заголовками та високошвидкісного лексичного ретрівалу за допомогою `bm25s` (досвід `Sabofxx`).
- **Запозичення найкращих інженерних практик:**
  - *Незмінність та швидка дедуплікація:* Використання конфігурації `frozen=True` у моделях джерел (`69Nesta`).
  - *Жорсткі обмеження:* Валідація розміру чанка $0 < \text{max\_chunk\_size} \le 2000$ на рівні моделей та CLI (`69Nesta`).
  - *Типізована фільтрація:* Підтримка категорій файлів `FileType` (`all`, `docs`, `code`) для ізольованої оптимізації ретрівалу (`69Nesta`).
  - *Лексичне збагачення:* Включення токенізованого шляху файлу в корпус BM25 (`69Nesta`).
  - *Надійне кешування та інкрементальність:* Розрахунок SHA-256 хешів файлів та кешування запитів із валідацією стану індексу (`Yanru`).
  - *Мінімалістичний сервер:* Чисті маршрути FastAPI без зайвих прошарків (`sousampere`).

## 2. Огляд модульної структури проєкту

Архітектура має відповідати принципу єдиної відповідальності (Single Responsibility Principle). Кожен файл повинен бути компактним (50–150 рядків), самодокументованим і містити ізольовану діагностичну секцію (`if __name__ == '__main__':`) для модульної верифікації без запуску всього комплексу:

```text
RAG_42Ber/
├── Makefile                     # Автоматизація: install, run, debug, clean, lint, test
├── pyproject.toml               # Конфігурація проєкту та залежності для uv
├── uv.lock                      # Детерміновані версії пакетів
├── README.md                    # Звіт, архітектурний опис та інструкція користувача
│
├── api/
│   └── app.py                   # Бонус 5: Локальний FastAPI HTTP-сервер (/search, /answer)
│
├── src/
│   ├── __init__.py              # Пакетний маркер
│   ├── __main__.py              # Вхідна точка CLI для команди python -m src <command>
│   ├── models.py                # Pydantic-моделі даних згідно з Chapter VI.4
│   ├── tokenizer.py             # Мінімальний токенайзер-скелет (bm25s, lower, stopwords)
│   ├── ingest.py                # Сканування каталогу, фільтрація файлів, безпечне зчитування
│   ├── chunking.py              # Чанкінг Python (AST) та Markdown (Headers) із контролем зміщень
│   ├── index.py                 # Побудова, збереження, завантаження BM25s та пошуковий рушій
│   ├── hash.py                  # Бонус 3: Хешування файлів SHA-256 для інкрементальності
│   ├── cache.py                 # Бонус 4: Дисковий кеш повторних запитів
│   ├── evaluator.py             # Розрахунок перекриття символів IoU >= 0.05 та Recall@k
│   ├── generator.py             # Генерація відповідей на базі Qwen3-0.6B із цитуванням контексту
│   └── cli.py                   # Реалізація 6 обов'язкових команд через Python Fire
│
├── data/
│   ├── raw/vllm-0.10.1/         # Вхідний корпус вихідного коду та документації vLLM
│   ├── processed/               # Серіалізовані індекси (bm25, dense, chunks.json, hashes.json)
│   ├── datasets/                # Вхідні датасети (UnansweredQuestions, AnsweredQuestions)
│   └── output/                  # Результати виконання пошуку та генерації відповідей
```

### Крок 1.2: Специфікація конфігурації проєкту (`pyproject.toml`)
Конфігурація має спиратися на сучасний стандарт PEP 621 та менеджер пакетів `uv`.

- **Вимоги до конфігурації:**
  - Назва проєкту: `rag-against-the-machine`.
  - Версія інтерпретатора: Python `>=3.10`.
  - Обов'язкові runtime-залежності:
    - `pydantic>=2.6.0`: сувора типізація та валідація схем даних.
    - `fire>=0.6.0`: автоматична побудова CLI-інтерфейсу.
    - `tqdm>=4.66.0`: індикація прогресу обробки файлів та чанків.
    - `bm25s>=0.2.0` разом із `PyStemmer>=2.2.0`: високоефективний лексичний ретрівал.
    - `transformers>=4.44.0`, `torch>=2.2.0`, `accelerate>=0.30.0`: інференс локальної LLM.
    - `sentence-transformers>=2.7.0`, `numpy>=1.26.0`: векторні ембедінги (Бонус 1 та 2).
    - `fastapi>=0.110.0`, `uvicorn>=0.28.0`: HTTP REST API (Бонус 5).
  - Dev-залежності: `flake8>=7.0.0`, `mypy>=1.10.0`, `pytest>=8.0.0`.
  - Налаштування `mypy`: суворий аналіз типізації (`warn_return_any = true`, `disallow_untyped_defs = true`, `check_untyped_defs = true`).
  - Налаштування `flake8`: ліміт довжини рядка 100 символів, сумісність із PEP 8.

- **Процедура встановлення:**
  ```bash
  uv sync
  ```

### Крок 1.3: Специфікація автоматизації задач (`Makefile`)
Файл `Makefile` повинен реалізовувати стандартні таргети, передбачені регламентом 42 (Chapter V.2):

- **Таргети автоматизації:**
  - `install`: синхронізація залежностей через `uv sync`.
  - `run`: запуск індексації корпусу за замовчуванням (`uv run python -m src index --max_chunk_size 2000`).
  - `debug`: запуск індексації в інтерактивному дебаггері Python (`pdb`).
  - `clean`: очищення тимчасових кешів (`__pycache__`, `.mypy_cache`, `.pytest_cache`) та артефактів індексації у `data/processed/*`.
  - `lint`: запуск базової перевірки `flake8` та `mypy`.
  - `lint-strict`: запуск повної суворої перевірки `mypy --strict`.
  - `api`: запуск HTTP сервера через `uvicorn` на порту 8000.

- **Команда перевірки працездатності оточення:**
  ```bash
  uv run python -c "import pydantic, fire, tqdm, bm25s, torch, transformers; print('Dependencies OK! Torch version:', torch.__version__)"
  ```
- **Очікуваний результат:**
  ```text

  ```

## Етап 2: Pydantic моделі даних (Data Models)

### Крок 2.1: Специфікація моделей даних (`src/models.py`)
Модуль повинен реалізовувати суворі схеми даних, що до байта відповідають розділу Chapter VI.4 специфікації.

- **Специфікація класів та контрактів:**
  - `FileType(str, Enum)`: перелік категорій файлів із константами `ALL = "all"`, `DOCS = "docs"`, `CODE = "code"`.
  - `MinimalSource(BaseModel)`:
    - Поля:
      - `file_path: str`: відносний шлях до файлу від кореня проєкту.
      - `first_character_index: int`: початковий індекс символу (включно).
      - `last_character_index: int`: кінцевий індекс символу (виключно).
    - Конфігурація: `model_config = ConfigDict(frozen=True)`. Об'єкти мають бути хешованими (`hashable`), незмінними, що унеможливлює випадкову мутацію символьних меж і дозволяє миттєву дедуплікацію ретріваних джерел через множину `set()`.
  - `UnansweredQuestion(BaseModel)`:
    - Поля:

## Етап 3: Мінімальний токенайзер-скелет (навчальний)

> **Принцип скелета:** спочатку наскрізний ланцюжок `load → chunk → index → retrieve` на мінімальному коді, щоб зрозуміти сам принцип RAG. Ускладнення (camelCase/snake_case преспліт, фільтр довжини, збагачення тексту) — відкладені покращення, а не частина скелета.

### Крок 3.1: Специфікація токенайзера (`src/tokenizer.py`)
Мінімальна обгортка над `bm25s.tokenization.Tokenizer`, один в один як в еталонному прикладі. Ідентифікатори лишаються цілими (`VLLM_RPC_TIMEOUT` -> `vllm_rpc_timeout`) — це свідоме рішення "start simple".

  - Приведення всіх термів до нижнього регістру (`lower=True`).

## Етап 5: Стратегії чанкінгу Python (AST) та Markdown (Headers)

### Крок 5.1: Специфікація структури чанка та правил розбиття
Чанк є базовою одиницею пошуку.

- **Вимоги до об'єкта `Chunk`:**
  - Поля: `file_path: str`, `first_character_index: int`, `last_character_index: int`, `text: str`.
  - Метод: `char_len() -> int`.
  - **Головний математичний інваріант:**
    `file_content[first_character_index:last_character_index] == text`
    Невідповідність цього інваріанта призводить до дискваліфікації рішення тестуючою системою.
  - **Обмеження розміру:** довжина тексту кожного фрагмента не повинна перевищувати `max_chunk_size` (жорсткий ліміт Moulinette $\le 2000$ символів).
  - **Алгоритм ковзного вікна (`_split_oversized`):** якщо природний структурний блок перевищує `max_chunk_size`, він ділиться ковзним вікном із перекриттям (overlap) $10\%$ від розміру вікна (`max_chunk_size // 10`).

---

### Крок 5.2: Специфікація алгоритму AST-чанкінгу для Python
Обробка коду через абстрактні синтаксичні дерева (`ast`) гарантує семантичну цілісність логічних одиниць.

- **Вимоги до логіки AST-розбиття:**
  - Побудова AST за допомогою модуля стандартної бібліотеки `ast.parse(text)`.
  - При виявленні синтаксичної помилки (`SyntaxError`) — плавний перехід (fallback) до звичайного поблокового розбиття тексту.
  - Розрахунок масиву символьних зміщень кожного рядка вихідного файлу для швидкої конвертації пар `(lineno, col_offset)` у глобальний символьний індекс файлу.
  - Виділення верхньорівневих вузлів: класи (`ast.ClassDef`), функції (`ast.FunctionDef`, `ast.AsyncFunctionDef`).
  - Фіксація блоків коду, що передують функціям (імпорти, глобальні змінні, константи).
  - Фіксація «хвоста» файлу, розташованого після останнього оголошення.
  - Застосування `_split_oversized` до будь-якого отриманого сегмента, що перевищує ліміт.

- **Сигнатура функції:**
  - `chunk_python(file_path: str, text: str, max_chunk_size: int = 2000) -> List[Chunk]`

### Крок 5.3: Специфікація алгоритму Markdown-чанкінгу
Документація структурується навколо заголовків різного рівня.

- **Вимоги до розбиття Markdown:**
  - Ідентифікація рядків, що починаються з одного або декількох символів `#` (ATX headers: `#`, `##`, `###`).
  - Визначення початкових зміщень розділів. Якщо перший рядок не є заголовком, початковий блок відраховується від індексу 0 (вступна частина).
  - Формування діапазонів між сусідніми заголовками від попереднього до наступного.
  - Розбиття завеликих секцій через ковзне вікно `_split_oversized`.

- **Сигнатури функцій:**
  - `chunk_markdown(file_path: str, text: str, max_chunk_size: int = 2000) -> List[Chunk]`
  - `chunk_file(file_path: str, text: str, max_chunk_size: int = 2000) -> List[Chunk]`: диспетчер, що обирає `chunk_python` для `.py` файлів та `chunk_markdown` для `.md`, `.rst`, `.txt`.

## Етап 7: Оцінка якості Recall@k та валідація на датасеті

### Крок 7.1: Специфікація метрик та оцінювача (`src/evaluator.py`)
Оцінювач має реалізовувати суворі правила оцінки згідно з розділом Chapter VII.1 специфікації.

- **Специфікація формул та правил:**
  - *Точність шляху:* знайдений фрагмент зараховується лише за умови $100\%$ збігу шляху файлу (`retrieved.file_path == truth.file_path`).
  - *Перекриття символів (Intersection over Ground Truth):*
    $$IoU = \frac{|Retrieved \cap Truth|}{|Truth|} = \frac{\max(0, \min(R_{end}, T_{end}) - \max(R_{start}, T_{start}))}{T_{end} - T_{start}}$$
  - *Поріг валідності:* $IoU \ge 0.05$ ($5\%$).
  - *Recall@k для одного питання:* частка еталонних джерел питання, які мають хоча б один валідний перетин серед перших $k$ ретріваних джерел.
  - *Глобальний Recall@k:* середнє арифметичне Recall@k за всіма запитаннями датасету.
  - Клас звіту `EvalReport`: формує форматовану таблицю метрик для $k \in (1, 3, 5, 10)$ з відміткою `(PASS >= 80%)` для Recall@5.

---

### Крок 7.2: Процедура та критерії валідації Recall@5 на датасеті
Модуль повинен протестувати розрахунок IoU на синтетичних випадках (частковий збіг, невідповідний файл) та перевірити відповідність пороговим значенням.

### Крок 9.1: Специфікація інтерфейсу командного рядка (`src/cli.py`)
Клас `CLI` є точкою входу для взаємодії користувача та автоматизованої Moulinette (Chapter VI.6).

- **Специфікація 6 обов'язкових команд:**
  1. `index(repo_path="data/raw/vllm-0.10.1", save_directory="data/processed", max_chunk_size=2000)`:
     - Валідація: $0 < \text{max\_chunk\_size} \le 2000$. Якщо значення некоректне або папка не існує — вивід помилки у `sys.stderr` без аварійного traceback.
  2. `search(query, k=10, index_directory="data/processed", file_type="all")`:
     - Захист від дегенеративних входів: якщо запит пустий або $k \le 0$ — негайне повернення JSON `[]`.
     - Вивід результату: валідний JSON-список об'єктів `MinimalSource`.
  3. `search_dataset(dataset_path, k=10, save_directory="data/output/search_results", index_directory="data/processed", file_type="all")`:
     - Зчитування запитань, виконання пошуку, формування структури `StudentSearchResults` та збереження у файл JSON за оригінальною назвою датасету.
  4. `answer(query, k=5, index_directory="data/processed")`:
     - Пошук top-k контекстів та генерація відповіді моделлю Qwen.
  5. `answer_dataset(student_search_results_path, save_directory="data/output/search_results_and_answer", index_directory="data/processed")`:
     - Завантаження результатів пошуку, зіставлення чанків за координатами, генерація відповідей для кожного питання та збереження контейнера `StudentSearchResultsAndAnswer`.
  6. `evaluate(student_search_results_path, dataset_path)`:
     - Порівняння результатів студента з еталонними джерелами датасету та вивід таблиці Recall.

- **Специфікація `src/__main__.py`:**
  - Передає клас `CLI` у виклик `fire.Fire(CLI)`.

### Крок 10.2: Специфікація Бонусу 2 (Гібридний пошук Hybrid RRF)
- **Вимоги до алгоритму Reciprocal Rank Fusion:**
  - Об'єднання лексичного списку кандидатів BM25 та векторного списку кандидатів Dense.
  - Формула ранжування:
    $$RRF\_Score(d) = \sum_{m \in \{BM25, Dense\}} \frac{1}{60 + rank_m(d)}$$
  - Дедуплікація чанків та сортування за спаданням сумарного балу $RRF\_Score$.

---

### Крок 10.3: Специфікація Бонусу 3 (Інкрементальна індексація SHA-256)
- **Вимоги до модуля `src/hash.py`:**
  - Функція `compute_hash(text: str) -> str`: розрахунок 64-значного SHA-256 хешу вмісту файлу.
  - Функція `diff_hashes(old_hashes, current_hashes) -> Tuple[Set[str], Set[str]]`: повертає множини `(змінені_або_нові_файли, видалені_файли)`.
  - Збереження хешів у `data/processed/hashes.json`. При виклику `index` оновлюються лише чанки змінених файлів, що скорочує час переіндексації з кількох хвилин до кількох секунд.

- **Команда перевірки модуля хешів:**
  ```bash
  uv run python -c "from src.hash import compute_hash, diff_hashes; print('Hash OK:', compute_hash('test'))"
  ```
